# Прямой IPv4 и выбранный IPv6 в режиме сервисов

На Windows Server 2022 сбой воспроизведён с ядром и Wintun из опубликованного установщика 0.3.56 (SHA-256 a3e82577f8e7f00f62a707a900f2a43c904e291e36d3fbc7a19fb8e4975246db). Проверялись Telegram, WhatsApp, ChatGPT, YouTube, Speedtest и свои домены. Запросы к GitHub, принудительно использовавшие IPv4, проходили, а HTTPS Яндекса с обычным выбором семейства адресов обрывался. В журнале ядра зафиксировано: dial tcp [2a02:6b8::2:242]:443 / unreachable network, а curl получал reset соединения. Предыдущая проверка: https://github.com/stisvladnext3-creator/moskompremont/actions/runs/45062059567 .

Исправленная конфигурация проходит проверку с тем же опубликованным ядром: https://github.com/stisvladnext3-creator/moskompremont/actions/runs/45063029479 . Перед TUN прошёл прямой IPv4-запрос к Яндексу. Проверка наличия IPv6-маршрута вернула False. Затем прошли настоящие TUN, DNS и HTTPS Яндекса, собственные домены через прокси, передача более 128 КБ для IPv4/IPv6 адресов Telegram и WhatsApp, сохранение AAAA для выбранного сервиса, обычное отключение и очистка после аварийного завершения. Все 52 .NET unit-теста прошли.

Новая DNS-логика применяется только в режиме сервисов при отсутствии IPv6-маршрута до поднятия TUN. Пустой NOERROR для AAAA получают только невыбранные имена; выбранные домены, поддомены, точные full: и IPv6-адреса продолжают маршрутизироваться через прокси. Системные настройки IPv6 не меняются.

## Not run

Физический компьютер пользователя и его провайдер не подключены. Стенд использует Windows Server 2022 и локальный SOCKS-прокси с вымышленными ответами для выбранного трафика; запросы Яндекса и обычного сайта выполняются действительно напрямую. Проверки полных установщиков выполняются штатными workflow Windows/macOS после включения изменения в main.
