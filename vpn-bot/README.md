# Telegram-бот для VPN

Бот принимает обращения клиентов, уведомляет владельца о сбоях и выдаёт личные
резервные VLESS-ссылки из пула 3x-ui. Узел в России запускает настоящий Xray-клиент
и выполняет HTTPS-запрос через проверяемый inbound. Вторую проверку выполняет
контроллер за пределами РФ.

По умолчанию цикл — 30 секунд, тайм-аут — 8 секунд. Уведомление о недоступности
отправляется после двух последовательных неудач, о восстановлении — после двух
успехов. Отсутствие отчётов от российского узла в течение 120 секунд означает
«нет свежих данных», и его старые результаты не разрешают выдачу резерва.
Уведомления сохраняются в SQLite и повторяются при временной недоступности Telegram.

```
3x-ui ← API ← Бот / контроллер → Telegram: владелец и клиенты
                  ↑
              HTTPS + токен
                  ↑
            Узел в России
                  ↓
       Xray → VPN inbound → проверочный HTTPS-сайт
```

## Что уже реализовано

- Совместимость с API 3x-ui 2.x (сессия) и 3.x (API-токен/новый clients API).
- VLESS с Reality/TLS, TCP/raw, gRPC, WebSocket, HTTPUpgrade, базовым XHTTP.
- Создание 15 свободных резервных учётных записей суммарно по настроенным серверам.
  Для нового клиента `enable=true`, `expiryTime=0`, `totalGB=0`: срок и лимит трафика
  не отключат такой ключ. Тарифные/серверные ограничения остаются у владельца.
- Отдельный мониторинговый клиент на каждый inbound. Личные клиентские ключи
  не передаются российскому проверяющему узлу.
- Контроль отключения, срока и квоты известных резервных клиентов каждые 5 минут.
  Существующие настройки пользователей в панели не переписываются.
- Допуск клиентов владельцем, заявки, текст/фото/документы поддержки, ответы владельца.
- Атомарное закрепление ключа за одним пользователем, без повторной выдачи другому.
- Резерв выдаётся только при свежем успешном **VPN-запросе из РФ**. Открытый TCP-порт
  и успешная проверка из другой страны этого разрешения не дают.
- Отчёты проверяющих узлов аутентифицированы, ограничены по размеру, проверяются
  по времени и версии профиля; повторная доставка одного отчёта не создаёт ложных сбоев.

Если основной сервер уже недоступен, предпочтение получает исправный резерв на
другом адресе. При одном сервере все 15 ключей зависят от одного IP и одного inbound.
Для устойчивости к блокировке адреса добавьте второй сервер/адрес в `servers`.
Сам пул ключей не может гарантировать постоянную доступность IP из всех сетей РФ.

## 1. Настройки

Создайте Telegram-бота через `@BotFather`, получите токен и свой **числовой** Telegram ID.
ID администраторов задаются явно; первый написавший человек не становится владельцем.

```sh
cp config.example.toml config.toml
cp .env.example .env
chmod 600 .env
chmod 644 config.toml
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Случайную строку из последней команды сохраните в `PROBE_RU_TOKEN` на контроллере
и на российском узле. В `.env` заполните `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_IDS`
и данные 3x-ui. В config.toml хранятся адреса и имена переменных, а секреты — в .env. Контейнер читает конфиг от отдельного пользователя. Значения секретов не публикуются в Git и не выводятся в журналы.

В `config.toml` замените примеры на ваши панели и inbounds. Для одного сервера
оставьте один `[[panels]]` и один `[[servers]]`; все 15 резервов будут на нём.
`host` — адрес подключения VPN-клиента; порт берётся из inbound через API панели.

`base_url` включает скрытый webBasePath 3x-ui, но **без** завершающего `/panel/`.
Например, для страницы `https://panel.example/hidden/panel/` укажите
`https://panel.example/hidden/`. Если используется собственный CA, настройка
описана в [deploy/README.md](deploy/README.md).

3x-ui 3.x: создайте API-токен с правами чтения inbound/клиентов и создания клиентов,
укажите `token_env`. 3x-ui 2.x: уберите `token_env`, задайте `api_mode="legacy"`,
`username_env` и `password_env`, а их значения — в `.env`. Вход с интерактивной
2FA в этой версии не поддерживается: используйте API-токен на поддерживающей его панели.

Пример для **inbound 25, gRPC**:

```toml
[[servers]]
id = "vpn-main"
name = "Основной VPN"
panel = "main"
inbound_id = 25
host = "vpn-server.example.com"
flow = ""
check_url = "https://www.google.com/generate_204"
expected_status = 204
```

Для gRPC оставьте `flow=""`. `xtls-rprx-vision` применяется к TCP/raw.
SNI, публичный Reality-ключ, shortId, gRPC serviceName и порт бот читает из панели.
Приватный Reality-ключ остаётся на контроллере; агент получает только клиентский профиль.

## 2. Контроллер

Нужен сервер с Docker Compose, доступом к Telegram и к API 3x-ui. Для сравнительной
проверки разместите его вне РФ и оставьте `local_probe_id="control"`.
Проверьте `region` каждого узла: это указанное владельцем место проверки,
автоматическое определение страны не выполняется.

```sh
docker compose build
docker compose run --rm bot validate
docker compose run --rm bot seed
docker compose up -d
docker compose logs --tail=50 bot
```

`seed` создаёт недостающие резервные клиенты и отдельного мониторингового клиента
на каждом inbound. Повторный запуск сохраняет существующие ключи. В конфигурации
с двумя серверами резерв 15 распределяется 8 + 7. Ключи сохраняются в базе данных,
в консоль они не печатаются.

На собственном сервере с открытыми 80/443 можно использовать Caddy:

1. Направьте DNS имени `monitor.example.com` на контроллер.
2. Укажите это имя в `MONITOR_DOMAIN` файла `.env` и в `controller_url` конфига.
3. Выполните:

```sh
docker compose -f compose.yml -f compose.public.yml up -d
```

Caddy получает публичный TLS-сертификат автоматически. Если на сервере уже есть
Nginx/сайт на портах 80/443, используйте существующий HTTPS-сервер и пример
[deploy/nginx.conf.example](deploy/nginx.conf.example). Сам API слушает только
`127.0.0.1:8080` на хосте. Входящие порты боту Telegram не нужны: используется polling.

Откройте своего бота и отправьте `/start`. Каждый администратор должен сделать это,
чтобы Telegram разрешил доставку уведомлений в его личный чат.

## 3. Узел в России

На российский сервер перенесите исходники и `config.toml`. Создайте **отдельный**
файл окружения, содержащий только токен этого узла:

```sh
cp .env.probe.example .env.probe
chmod 600 .env.probe
# Впишите тот же PROBE_RU_TOKEN, который указан на контроллере.
docker compose -f compose.probe.yml build
docker compose -f compose.probe.yml up -d
docker compose -f compose.probe.yml logs --tail=30 probe
```

Токен Telegram и пароли/API-токены 3x-ui на узле в России не нужны. Входящие порты
ему также не нужны: задания и отчёты проходят через исходящий HTTPS к контроллеру.
Синхронизируйте часы (NTP). Доступ к VPN-серверам должен идти через обычное
интернет-подключение узла, иначе измеряется другой сетевой маршрут.

В `/status` дождитесь успешного `VPN-запроса` от российского узла. Если Xray не
запустился, запрос не прошёл или отчёт устарел, автоматической выдачи не будет.
Проверка, названная «порт», подтверждает только TCP-доступность.

## 4. Команды

Клиент: `/start`, `/help`, `/status`, `/link`, `/myid`. Обычное сообщение, фото
или документ создаёт обращение. Владелец видит его с номером и ID клиента.

| Команда владельца | Действие |
| --- | --- |
| `/users` | Ожидающие подтверждения пользователи |
| `/allow 123456789` | Открыть доступ клиенту |
| `/deny 123456789` | Закрыть выдачу новых ссылок |
| `/status` | Состояние с каждой точки проверки |
| `/check` | Внеочередная локальная проверка; РФ проверит в ближайшем цикле |
| `/pool` | Количество свободных и выданных резервов |
| `/pool fill` | Пополнить свободный резерв до `pool_target` |
| `/issue 123456789` | Выдать допущенному клиенту новый проверенный резерв |
| `/tickets` | Открытые обращения |
| `/reply 12 текст` | Ответить на обращение №12 |
| `/close 12` | Закрыть обращение |

На копию обращения можно ответить обычной кнопкой «Ответить» в Telegram.
Команды владельца и выдача ссылок работают только в личных чатах.
При `automatic_links=false` команда клиента `/link` создаёт запрос владельцу.

Клиенту с уже работающей ссылкой `/link` возвращает её же. При проблеме выбирается
свежий проверенный резерв. `issue_cooldown` ограничивает частую замену; владелец
может выполнить `/issue` без этого ограничения. Без подтверждённого VPN-теста из РФ
ссылка не выдаётся и при `/issue`.

`/deny` запрещает выдачу через бота, но не отзывает уже импортированный ключ.
Отзыв существующего VPN-доступа выполняйте в 3x-ui. Уже выданные ключи не удаляются
автоматически при пополнении пула.

## Данные, обновление и границы проверки

База в Docker volume `bot-data` содержит ссылки, закрепление за пользователями,
метаданные обращений и очередь доставки. Сохраняйте резервную копию. При удалении
базы бот теряет историю закрепления ключей; не используйте `docker compose down -v`
при обновлении. Работает один контроллер на одну базу и один пул учётных записей.

Для согласованной копии остановите бота перед копированием volume либо используйте
SQLite backup API. Для обновления: `git pull`, `docker compose build`,
`docker compose up -d`; volume сохраняется. После восстановления базы сначала
сверьте выданные ключи с панелью.

Проверяется реальный трафик через указанный inbound и его серверную маршрутизацию.
Если маршрутизация зависит от email клиента, включите мониторингового клиента
`vpn-watch-<server_id>-probe` в то же правило, что проверяемый маршрут. Один
проверочный URL не доказывает работу всех сайтов: для разных целевых сервисов
можно настроить отдельные проверяемые inbounds/URL. Время в мс — длительность
запроса через VPN с установлением соединений, не ICMP ping.

Заявленная доступность относится к провайдеру российского узла. Дополнительные
узлы на других провайдерах и `min_ru_successes` позволяют требовать несколько
независимых подтверждений. HTTPS-сервис для проверки можно заменить своим.

Автоматический выпуск пока рассчитан на обычный VLESS Encryption `none`.
VMess/Trojan, нестандартный TCP HTTP-header, XHTTP extra и интерактивная 2FA
выдают понятную ошибку вместо объявления непроверенного соединения исправным.

## Разработка и проверки

Python 3.12+, Docker-образ включает Xray 26.10.31 с проверкой опубликованного SHA-256;
доступны архитектуры amd64 и arm64.

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt -e .
python deploy/install_xray.py ./bin/xray
XRAY_TEST_BINARY="$PWD/bin/xray" pytest -q
```

Проверки используют имитацию Telegram/3x-ui и настоящий локальный Xray. Они не
создают пользователей на реальных серверах и не отправляют сообщения в Telegram.
Без `XRAY_TEST_BINARY` проверки реального Xray пропускаются. Подключение к вашим
боевым серверам выполняется после заполнения секретов и запуска узла в РФ.
